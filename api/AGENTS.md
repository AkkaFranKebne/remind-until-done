# AGENTS.md: api/ (Go service)

Also read the root [`AGENTS.md`](../AGENTS.md). Design: design doc Appendix D (layout, interfaces) and section 3 (dispatcher).

## Commands
Run in `api/`. Needs Go (version in `go.mod`).

| Task | Command |
|---|---|
| Local database (from the repo root) | `make db-up migrate` · `make db-info` · `make psql` · `make db-reset` |
| Run on :8080 | `make run` (uses the local database) |
| Fire a push by hand, like Cloud Tasks | `make fire ID=<reminder id> V=<version> N=<push number>` (the API log prints the exact command for every booked task) |
| Run the daily sweep by hand, like Cloud Scheduler | `make sweep` |
| After editing `db/seed/messages.csv` | `make messages` (checks the rules, regenerates `db/migrations/R__nag_messages.sql`; touches no database: Flyway loads the file, locally with `make migrate`, on dev and prod in the deploy). Steps: the `edit-nag-lines` skill |
| Format check / vet / tests | `make fmt vet test` (Docker must be running) |
| Docker image | `make docker` (Docker Desktop must be running) |
| Known vulnerabilities | `go run golang.org/x/vuln/cmd/govulncheck@latest ./...` |

## Rules
- Use the `gopls` MCP server (root `AGENTS.md`) to find definitions, references and a package's API before changing shared code; run its diagnostics after a change.
- Layout follows Appendix D: `cmd/api` (wiring), `internal/config`, `internal/httpapi` (HTTP only), feature packages (`reminders`, `dispatch`, ...).
- `httpapi` only translates HTTP to service calls. Business rules live in the feature packages.
- Only `auth`, `scheduling` and `push` import Google SDKs. Everything else uses their interfaces (`httpapi.TokenVerifier`, ...), so tests can use fakes.
- Public routes live under `/api/v1/` (Firebase Hosting forwards the full path). Cloud Tasks and Scheduler call `/internal/*`.
- Internal routes are listed in `API.internalRoutes()` (not in `swagger.json`). `Router` wraps every `/internal/*` path in `requireInvoker`: a Google ID token (OIDC) signed by Google, issued by Google sign-in, made for `SERVICE_URL`, from `INVOKER_SA_EMAIL` with a verified email (`auth.Invoker`, design doc 7.1). The Cloud Run URL is public (Hosting must reach it), so this check is the only lock. Locally `make run` sets `INTERNAL_AUTH=off` (nothing signs tokens there); config refuses it in dev and prod.
- Routes are listed once in `API.routes()` (`internal/httpapi/router.go`). Every route except `/healthz`, `/actions` and `DELETE /me` (decision 79) is wrapped in `requireUser` (401 without a valid token, 403 `not_invited` if not on the invite list). Every route must be in `swagger.json`, and every `swagger.json` route must be served or listed in `notBuiltYet` (with its milestone): `router_contract_test.go` fails otherwise. Building a route? Remove it from `notBuiltYet`. The web app's API code is generated from `swagger.json`.
- The invite list (`ALLOWED_EMAILS`) works the same everywhere: listed and verified emails only; empty = nobody (design doc decision 31). Locally, put your Gmail in `api/.env.local` (`ALLOWED_EMAILS=you@gmail.com`; git-ignored).
- Errors use one JSON shape: `{"error":{"code":"...","message":"..."}}` (`writeError` in `internal/httpapi/errors.go`).
- Every answer (errors too) gets `Cache-Control: no-store` and `X-Content-Type-Options: nosniff` from `apiHeaders` (`internal/httpapi/middleware_headers.go`). Answers are per user, so no phone or CDN may keep a copy. Don't override it in a handler.
- Logs: structured JSON through the logger from `internal/logging` (Cloud Logging reads `severity` and `message`).
- Settings come from env vars in `internal/config`. Terraform sets them on Cloud Run (`infra/cloud_run.tf`).
- Database: one pgx pool (`internal/db`), created in `cmd/api/main.go` and passed down. In dev and prod the API logs in as `rud_app` (`V4__app_role.sql`, decision 86): read and write rows only, no table changes; Flyway uses the owner's login from `database-migrate-url`. `dbtest.Start` returns a pool working as `rud_app`, so every database test proves that's enough; a test that breaks the schema on purpose uses `dbtest.AsOwner`. A new migration's tables and sequences get the rights by default (`ALTER DEFAULT PRIVILEGES`), as long as Flyway's owner makes them. In dev and prod `db.Config` always turns on TLS with a certificate check for the host (system roots; Neon's certificate is from Let's Encrypt), whatever sslmode the URL says, and drops non-TLS fallbacks (decision 86). Locally the URL decides (the docker database has no TLS). Flyway in `deploy.yml` gets the same check from `scripts/to_jdbc.py` (`sslmode=verify-full` with `DefaultJavaSSLFactory`, Java's trusted roots). Packages take a small interface (like `httpapi.Pinger`), so tests can pass a fake.
- Schema changes are Flyway files in `db/migrations/` named `V<n>__<what>.sql` (`R__nag_messages.sql` is generated, and is the only repeatable one). They must work with the previous release too (design doc 6.5): add a nullable column, backfill, tighten later.
- Database tests use testcontainers (`dbtest.Start(t)`: a throwaway Postgres per test, same image as `docker-compose.yml`). Unit tests use fakes.
- Every reminder query filters by the signed-in `user_id`. Another user's row returns 404, not 403. The one exception is `MarkDoneFromAction`, which has no signed-in user: its id must come from a verified action token, never from a request.
- Deleting an account (`DELETE /me`, design doc 5.7, decision 78): the user's row (cascades take their reminders, events, device and seen lines) and the Firebase user go in one database transaction, with the Firebase call before the commit: if it fails nothing is lost, and until the commit other requests still find the row. If the commit itself fails, the log says `firebase user deleted, row still there`: a retry within the token's hour finishes the job, and after that the row goes by hand. `auth.Accounts` is its own client on the service account's login (`auth.Firebase` only checks tokens and has none). Locally `auth.KeepAccounts`. Any valid sign-in may call it, invited or not (decision 79): it checks the token itself instead of `requireUser`, accepts Google sign-ins only, never makes a row, and answers 204 if the account is already gone. If someone's very first request overlaps their delete, an empty row can stay; a retry within the token's hour removes it, and after that it goes by hand. A deleted account's token works for up to an hour, so `requireUser` asks Firebase before making a row for a user it doesn't know (decision 76), only then; "don't know" answers 503, not 401, and makes no row. The role this needs must be on an environment before this code reaches it (`infra/service_accounts.tf`).
- Reminders (`internal/reminders`): creating one, or moving a done one to a new time, locks the user's row first (`lockUser`, `SELECT ... FOR UPDATE`), then counts active reminders. Always lock in the same order (user, then reminder), or two requests can wait for each other forever. `TestCreateWaitsForTheUsersLock` proves the lock is there.
- Devices (`internal/devices`, decision 40): one push device per user. The same token again keeps its id; a new token replaces the device with a new id; a token still saved for another user moves to the caller. Registering locks the user's row first (same order as reminders). Push tokens are never returned or logged.
- Scheduling (`internal/scheduling`, design doc 3.2): every push is one Cloud Task named `r-{id}-v{version}-n{n}`, booked through the `scheduling.Scheduler` interface (`CloudTasks` in dev and prod, `Log` locally with `SCHEDULER=log`, `Fake` in tests). `CloudTasks.Enqueue` tries up to 3 times when Cloud Tasks is `Unavailable` (a dropped connection; the client library doesn't retry CreateTask), all within `enqueueTimeout`. That's safe because the name is fixed: a retry of a booking that did get through answers `AlreadyExists`, which counts as booked. Other errors aren't retried. Create, and an edit that moves `dueAt`, book push 0 inside the same transaction and set `enqueued_version`; if Cloud Tasks fails, everything rolls back and the API answers 503 `unavailable`. An edit that changes the interval of a nagging reminder (`sent`, next nag booked) takes a new version and books its next nag the same way, at the last push plus the new interval, or the new interval from now if that has passed, never right away (decision 62); a reminder being sent right now is left alone, since recording that push books the next nag with the new interval. A first push beyond `scheduling.Horizon` (25 days) gets no task; the sweep books it later.
- Push (`internal/push`, design doc 3.3): `push.Sender` sends one data-only web push (no notification block: the service worker builds it) and answers an `Outcome`: `Accepted`, `TokenGone` (UNREGISTERED or SENDER_ID_MISMATCH: delete the device) or `TryLater` (everything else, including INVALID_ARGUMENT, which could be our own bug). `FCM` in dev and prod, `Log` locally, `Fake` in tests. Push tokens and reminder titles are never logged.
- Firing (`internal/dispatch`, design doc 3.3): `POST /internal/tasks/fire` claims the reminder with one `UPDATE` that matches the exact version and push number, so a stale, duplicate or late task does nothing (204). Every later update is limited to that claim (`status = 'sending'` plus version and number), so Done or a move during a send wins. The next nag is booked **after** the commit, and a failure there still answers 2xx: a retry would push twice; the sweep repairs the chain. Only `ErrTryLater` (503) and database errors (500) make Cloud Tasks retry. A retry within 2 minutes finds the claim still held and does nothing, answering 2xx, which ends the task. So a send that crashed, or a failed `recordSent`, `stop` or `release`, usually leaves the reminder in `sending` with no task and no more nags until the next daily sweep repairs it. Only a retry that first arrives after 2 minutes takes the claim over, so a push may go out twice after a crash, which the notification tag hides. The work after a send runs on its own context, so a caller hanging up doesn't leave it half done.
- The sweep (`internal/dispatch/sweep.go`, `sweep_repairs.go`, design doc 3.4): `POST /internal/sweep`, daily from Cloud Scheduler. It runs in the order a, c, b, d: step b books past-due reminders, which step c would otherwise see as lost and book twice. (a) gives back sends stuck in `sending` for 5 minutes. (c) rebooks first pushes and (d) rebooks nags that are 15 minutes late, each under a new version from the sequence, keeping the push number. (b) books push 0 for pending reminders whose `enqueued_version` isn't their `schedule_version` and that are due within `scheduling.Horizon` (past ones too: they fire at once), under the current version, and also picks up a rebooking of (c) that failed. The new version is saved before the booking, with no lock held during it, so Done never waits for Cloud Tasks; every update checks the row is still that version and state, so an edit or Done meanwhile wins. A successful rebooking adds a `sweep_rebooked` event. After 3 of them for one push number within 4 days the reminder gives up and shows as Overdue (`sweep_gave_up` event, decision 76); a Cloud Tasks outage doesn't count, and moving the reminder starts the count over. Batches of 200 with keyset paging, one failure doesn't stop it, and it stops after 2 minutes (Scheduler's deadline is 3); the next day does the rest. It answers 204 unless the database can't be read, and logs `sweep_repaired` with the counts (ERROR if anything failed, gave up or didn't finish). Retention (`retention.go`, design doc 7.4) runs last: done reminders after 180 days, events after 90, devices unseen for 270 unless their user still has a push to come (decision 77). A failed cleanup only counts and logs, so it never makes Scheduler repeat the repairs.
- Locally `make run` sets `PUSH=log` and `SCHEDULER=log`; config refuses both in dev and prod. Config also refuses a `GCP_PROJECT` that isn't `rud-<env>-...`: sign-in, Cloud Tasks and FCM all use it, and a wrong one would make every push fail as "token gone" and delete every device.
- A new schedule version always comes from `nextval('reminder_schedule_version_seq')`, never `+ 1` (decision 52): a rolled-back attempt may have booked its task, and a reused version would reuse its task name.
- Nag lines (`internal/messages`, design doc 3.8, decisions 67 and 68): people edit `db/seed/messages.csv`; `make messages` generates the repeatable Flyway file `db/migrations/R__nag_messages.sql`, which Flyway runs again whenever its text changes, in every environment. Never edit the SQL by hand: a test fails if it doesn't match the CSV. Ids run without gaps and are permanent: to retire a line set `active` to false (a line deleted from the end is retired too, but its id could then be reused by mistake). `messages.Check` holds the rules. No program of ours loads the lines in a deploy, because only Flyway and firebase-tools may run after the Google login. `Picker.Pick` takes a random active unseen line of the push's level (`LevelFor`, decision 66); when a user has seen them all, their seen lines of that level are forgotten. It doesn't mark the line as seen: `recordSent` does, only after FCM accepts, also when Done won during the send, and outside its transaction with a short timeout: a failure there is only logged, so a line can never stop the nags (decision 69). An empty level answers `FallbackLine`, so the lines never block a push. The reminder keeps the text of its page line in `reminders.line` (decision 70): `recordSent` saves the push's line in the transaction that counts it, `MarkDone` a level-5 line. `MarkDone` picks before its transaction and marks seen after it, each with a short timeout and a failure only logged, so a line can never stop Done; with no done line, `line` stays empty and the app uses its own text, never `FallbackLine`, which is a nag.
- Writing nag lines (design doc 3.8, decision 89): a line is read in a glance on a lock screen, so an active one has at most 60 characters (`messages.Check`). Short, plain and a little dry, like "This won't do itself. We checked." or "This task chose you. Don't let it down." Never:
  - lines about the notification itself, or wordplay on it ("This is your reminder, reminding you.", "A hug in notification form.");
  - a cute reminder with a personality ("This reminder dressed up for you.");
  - warmth with no joke ("A gentle nudge wrapped in good intentions.");
  - circular lines ("We nudge because we care. We care because we nudge.");
  - reassurance that undercuts the nag ("…and that's okay.");
  - filler openers ("Still here.", "Still waiting.", "A soft reminder that…"; on level 4 "After this notification…", which sounds like system text);
  - repeated words for effect ("Softly, gently, warmly, persistently");
  - "we", "us" or "our": the app has no narrator. The task can be the subject ("This task has settled in."), the line can talk to "you", or it can have no subject at all ("Last one. Tap Done."). The one kept exception is "This won't do itself. We checked.";
  - the word "app": say "rud." if a line needs a name;
  - a second sentence that only comments on the first ("Very cosy.", "Impressive.", "Probably.", "Just saying."). A second sentence must turn the meaning ("This task hasn't moved. Maybe you should.") or say what to do ("Tap Done.").

- Final nag lines (level 4) say plainly that this is the last nag, and what comes next: Done or overdue. Like "Last chance before overdue." or "Final nag. Done is right there." Never:
  - a vague "Last one." (the last what?);
  - stage, story and sports images ("Take a bow", "No encore", "swan song", "Curtain call", "The final whistle", "The last page", "Here's the pen", "has entered the chat");
  - silence or peace after it ("Make it a done silence.", "Then you're left in peace.");
  - lines about the nagging itself ("This is the goodbye nag.", "The nagging stops here.", "Then the nagging retires.");
  - clichés ("Go out on a high", "For real this time", "Make it count").
- Gentle lines (level 1) are short, direct and friendly, or bring in your future or past self. Like "This won't take long.", "You set this for a reason.", "Do this before you forget again.", "Remember this? It remembers you.", "A note from your calmer future self.", "Make it so." or "Engage!" Never:
  - patience lines ("The task is patient. The deadline isn't.", "Patience is vast. Not infinite.");
  - the list, checklist or to-do list acting on its own ("The list never forgets.", "Your to-do list flagged this.", "filed a missing persons report");
  - poetic or philosophical images ("the sound of one task waiting", "your unfinished symphony", "Soft as morning.");
  - proverbs and clichés ("The best time to do this was earlier.", "Done feels better than almost.", "Small tap. Big payoff.");
  - wordplay ("Still the task. Still the person.", "This exists. One tap and it doesn't.", "Set. Waiting. Done.");
  - deadline lines ("Deadlines are real.").
- Teasing lines (level 2) tease the delay with mock praise, a plot twist or a spoiler, or say that it's back again. Like "Plot twist: it still hasn't done itself.", "You're impressively good at ignoring things.", "Your delay has achieved a certain grandeur.", "Back again. You seem surprised. Don't be." or "This task has outlived some houseplants." Never:
  - lines about the reminder or notification itself ("The reminder remains.", "A regular in your notification tray.", "Designed not to go away.", "Soldiering on. As reminders do.");
  - the task taking up a hobby or a mood ("wrote a poem", "started a podcast", "started a newsletter", "developing a complex", "has gotten quite philosophical");
  - family, relationship or housemate images ("part of the family", "More commitment than most relationships.");
  - "noted", "notes are being taken", judging or cataloguing;
  - clipped lists ("Watching. Waiting. Judging a little.", "Task: patient. Reminder: relentless.");
  - big or abstract images ("the elephant in the notification tray", "A constant in your variable life.", "Growing more legendary").
- Last-call lines (level 3) are direct, or a funny exaggeration of how long the task has waited. Like "This is getting serious.", "'Later' is no longer acceptable.", "Enough delays to fill an autobiography." or "Standing in the rain, shouting your name." Never:
  - talk about phases, tone or escalation ("The gentle phase is over.", "From suggestion to strong recommendation.", "Escalated.", "Past subtle. At emphatic.");
  - "imploring", or alarm and volume images ("Sounding the alarm. Metaphorically.", "Full volume.");
  - wordplay on "urgent", "maximum" or "almost" ("Urgently not calm.", "You're maximum needed.", "Act in almost.");
  - lines that comment on themselves ("Look how not-messing-around this is.", "This is not a drill. Well.");
  - door, edge or last-stand images ("knocking on done's door", "The task's last stand").
- Done lines (level 5) are plain and warm, like "Done. Knew you had it in you." or "Done. That's a weight off. Go enjoy it." Never:
  - lines about the nagging or the app ("The nagging was worth it.", "The nag machine stands down.");
  - "until the next one" or the next reminder;
  - winning against the list or the deadline ("The to-do list didn't stand a chance.", "Task: defeated.");
  - big metaphors ("Write it in the sky.", "You're the protagonist now.", "Add it to your highlight reel.");
  - clipped word lists ("Nagged. Delivered.", "Celebrated. Moving on.");
  - a joke at the user's cost ("They'll be less impressed.", "Nobody's crying. You're crying.").
- Action tokens (`internal/actiontoken`, `POST /actions`, decision 72): each push carries a signed token that can only mark one reminder done, for 24 hours, until an edit changes its schedule version. It travels in the request body, never the address, because Cloud Run logs addresses. The signature is checked before the database is touched. `ACTION_TOKEN_KEY` is required in dev and prod (at least 32 bytes); locally config uses a fixed key that protects nothing. Tokens and the key are never logged.
- Rate limit (`internal/ratelimit`, `middleware_ratelimit.go`, design doc 7.2, decision 86): a token bucket per key, in memory on each instance, `RATE_LIMIT_PER_MINUTE` requests a minute (`config.DefaultRateLimitPerMinute`). `a.allow(w, r, key)` answers 429 `rate_limited` with `Retry-After` itself. It runs before any database call: in `requireUser` and `DELETE /me` right after the token check (key `user:<uid>`, also for someone not invited), in `POST /actions` right after the signature check (key `action:<reminder id>`). A request without a valid token or signature never counts. `DELETE /me` also runs one at a time per user on an instance (`inFlight`): it holds a database connection while Firebase answers, so a few at once during a Firebase slowdown could take the pool's connections; a second one answers 429. It checks the Google provider before the limit, so other sign-in methods can't make keys. Moves and interval changes are signed-in routes, so the user's limit covers the Cloud Tasks they leave behind. Every swagger.json route but `/healthz` documents the 429. The web app shows "Slow down a little. Try again in a minute." (`web/src/lib/api/errorText.ts`).
- Browser routes are listed in `API.browserRoutes()` (not in `swagger.json`: the browser calls them by itself, the generated web client never does). Today only `POST /csp-reports` (`handlers_csp.go`, design doc 7.1): Content-Security-Policy reports, no sign-in, one shared limit per instance (key `csp-reports`), a 16 KB body, never touches the database. Each report is one WARN line `csp violation`: the directive, the blocked address as origin only (an outside path can hold a token), the source file as origin + path (never a query or fragment), and the page path. Directives and words like `inline` must be plain keywords, else `other`. Anyone can post here, so a report can still name a made-up host; it can't add log lines or fields (the JSON log escapes values). Over the limit it answers 429 without the extra `rate limited` line.
- A public route that touches the database must not let anonymous callers wake or flood it: check once at startup (like `CheckDatabase` for `/healthz`), require sign-in, or refuse bad signatures before any query (like `/actions`).

## Never
- Never build SQL by string concatenation. Use query parameters. The one exception is `messages.RenderSQL`: it runs on a computer, from the reviewed CSV, never on user input.
- Never log secrets, ID tokens, emails or full connection strings (log the Firebase uid instead). Errors that could quote `DATABASE_URL` aren't wrapped (see `db.Open`).
- Never add an `/internal/*` route outside `internalRoutes()`, and never turn the OIDC check off outside `ENV=local`.
- Never edit an applied migration. Add a new one (design doc 6.5).
